# MeshPulse MVP (Phase 1) — design

Oct 16, 2026 · Builds Phase 1 of `docs/SPEC.md`. Where this document and the
spec differ, this document wins for the MVP.

## Goal

Know when the Zigbee network breaks. A passive, read-only monitor for one
Zigbee2MQTT instance that opens a small number of issues and sends them to
Discord without spam.

Exit criterion: a week against the real mesh with no false Critical.

## Decisions

| # | Topic | Decision |
| --- | --- | --- |
| Q1 | Silent end devices | Each device learns its typical message gap (rolling median of the last ~20 gaps). Silent when the current gap is longer than 3 × typical, clamped to 2–25 h. Until a device has enough gaps, only Z2M availability counts. |
| Q2 | Battery voltage | Voltage thresholds apply only to coin-cell devices: highest voltage ever seen ≤ 3.3 V. Other devices use battery %. |
| Q3 | Admin account | `ADMIN_EMAIL` and `ADMIN_PASSWORD` create the account on first start if none exists. Sign-up is disabled. |
| Q4 | Acknowledged issues | Acknowledge stops reminders only. Escalation and resolve messages still go out. |
| Q5 | Live updates | Pages reload their data every 15 s. No Server-Sent Events in the MVP. |
| Q6 | Mute | Mute applies to a device (1 h, 24 h, 7 d, forever). Muted issues stay visible but don't notify. |
| Q7 | Code | Private GitHub repo `jumpingmushroom/MeshPulse`. One branch and one squash-merged PR per milestone. |
| — | Battery rules | One issue per device: Warning at the low threshold, escalates to Critical at the critical threshold. |
| — | Flood guard | While `bridge.offline` or `monitor.mqtt_lost` is open, device-level issues don't open. |

## Out of scope for the MVP

`samples_hourly`, `baselines`, `health_samples`, `message_counts`,
`bridge_snapshots`, per-device threshold overrides, device detail page,
charts and sparklines, Batteries and Events pages, health score, weekly
digest, ntfy, Apprise, log parsing, every rule not listed below.

## Architecture

One Node process (SvelteKit, adapter-node). `src/hooks.server.ts` starts these
once:

- **Collector**: mqtt.js client on `${Z2M_BASE_TOPIC}/#`. Routes messages,
  keeps current state in memory, writes to SQLite. Never publishes.
- **Rules loop**: every 60 s, runs the rules, then the lifecycle.
- **Outbox worker**: every 2 s, delivers due messages.
- **Heartbeat**: every 60 s.

```
src/lib/server/
  db/schema.ts           Drizzle tables
  db/index.ts            better-sqlite3 connection, WAL, migrations
  mqtt/route.ts          pure: (state, topic, payload, retained, now) → state changes
  mqtt/collector.ts      connection and wiring
  rules/*.ts             one pure function per rule
  issues/lifecycle.ts    pure: findings + open issues → transitions + messages
  notify/channel.ts      Channel interface and registry
  notify/discord.ts      Discord webhook channel
  notify/outbox.ts       outbox worker
  heartbeat.ts, auth.ts, settings.ts, crypto.ts, retention.ts
src/routes/              overview, devices, issues, issues/[id], settings, login, api/health
scripts/capture.ts       records MQTT traffic to JSONL
tests/fixtures/          JSONL fixtures in the capture format
```

## Data model

SQLite via Drizzle, WAL mode. Timestamps are UTC epoch milliseconds,
displayed in `TZ` (default Europe/Oslo).

| Table | Columns | Notes |
| --- | --- | --- |
| `devices` | ieee (PK), instance_id (default `'default'`), friendly_name, alias, type, power_source, model, vendor, firmware, network_address, availability, last_seen_at, first_seen_at, removed_at, muted_until, tags (json: `chatty`, `ignore`), ignore_rules (json), typical_gap_ms, max_voltage | One row per device. `muted_until` = far future for "forever". |
| `samples` | ieee, ts, lqi, battery, voltage | At most one per device per 5 min, last value wins. Deleted after 14 days. |
| `events` | id, ts, ieee (nullable), kind, detail (json) | Availability changes, join, leave, announce, interview, bridge state, bridge restart, version change, battery swap. Deleted after 90 days. |
| `issues` | id, rule, ieee (nullable), severity, state (open/acknowledged/resolved), opened_at, updated_at, resolved_at, summary, action, evidence (json), last_notified_at, parent_issue_id | Unique index on (rule, ieee) where state ≠ resolved. Resolved issues deleted after 90 days. |
| `outbox` | id, channel_id, issue_id (nullable), kind, severity, message (json), dedupe_key (unique), status (pending/sent/failed), attempts, next_attempt_at, last_error, created_at, sent_at | Sent rows deleted after 7 days. |
| `channels` | id, kind, name, config (json, secrets encrypted), min_severity, enabled | Only `discord` in the MVP. |
| `settings` | key, value (json) | Thresholds, quiet hours, heartbeat URL. Defaults live in code. |
| Better Auth | user, session, account, verification | Generated by Better Auth. |

The retention job runs hourly with the rules loop.

In-memory only (rebuilt on start): current bridge info and state, the last
live message time, consecutive-run counters for open and resolve, and each
device's last ~20 message times. `typical_gap_ms` is written to the device row
hourly.

## Collector

Topics are matched by exact name against the name→IEEE map. Friendly names may
contain `/`.

| Topic | Action |
| --- | --- |
| `bridge/devices` | Upsert devices by IEEE, rebuild the name map. Devices missing from the list get `removed_at`. Returning devices clear it. |
| `bridge/info` | Store in memory: version, coordinator, channel, permit_join (and since when), config. A version change is logged as an event. |
| `bridge/state` | JSON `{"state":"online"}` or plain `online`. A change is logged as an event. Offline → online is logged as a restart. |
| `bridge/health` | Uptime lower than the previous sample is logged as a restart. Previous uptime is kept in memory. |
| `bridge/event` | `device_joined`, `device_leave`, `device_announce`, `device_interview` are logged as events. |
| `<name>/availability` | JSON or plain string. Only a change is logged as an event and written to `devices.availability`. |
| `<name>` | Live messages update `last_seen_at` (payload `last_seen` if present, otherwise now) and the message gaps. Writes a sample at most every 5 min. A battery rise of > 30 points is logged as a battery swap. Updates `max_voltage`. |
| Everything else | Ignored: `/set`, `/get`, unknown names (groups), `bridge/logging`, `bridge/request/*`, `bridge/response/*`, etc. |

Retained messages update current state but never count as live: they don't
update `last_seen_at` (unless the payload carries `last_seen`), the gaps, or the
last live message time.

Voltage is normalised to volts. Z2M reports millivolts on most devices, so a
value > 100 is divided by 1000.

## Prerequisites check

Read from `bridge/info.config`:

- `availability.enabled` (or `availability: true`) is true.
- `health` is configured.
- `advanced.log_output` includes `mqtt`.

The Overview and Settings pages show a banner for each missing setting. In the
MVP, log output only affects the banner, because route rules are Phase 2.

## Rules

Each rule is a pure function `(ctx) → Finding[]`. `ctx` holds current state,
recent events, settings, `now`, and the keys of the issues the rule already has
open, so rules can apply different start and stop conditions. A finding has
`rule`, `ieee`, `severity`, `summary`, `action`, `evidence`.

Devices tagged `ignore`, listed in `ignore_rules`, or removed produce no findings.

| Rule | Fires when | Severity | Stops when |
| --- | --- | --- | --- |
| `bridge.offline` | `bridge/state` offline, or no live message for 5 min | Critical | Online and live messages for 2 min |
| `bridge.restarted` | A restart event in the last hour | Info; Warning if ≥ 3 restarts in 24 h | 1 h after the last restart |
| `bridge.permit_join_open` | permit_join true for > 10 min | Warning | permit_join false |
| `monitor.mqtt_lost` | Broker connection down > 60 s | Critical | Connected |
| `device.offline` | Availability offline; or end device silent > 3 × `typical_gap_ms` (2–25 h) | Warning | Online and seen again. Resolve message includes downtime. |
| `device.flapping` | ≥ 4 availability changes in 6 h | Warning | < 2 changes in 6 h |
| `battery.low` | battery ≤ 25%, or `battery_low` true, or (coin cell) voltage ≤ 2.8 V | Warning; Critical at battery ≤ 10% or (coin cell) voltage ≤ 2.6 V | battery > 40% (or coin-cell voltage > 2.9 V) |

`battery.critical` is the Critical level of the `battery.low` issue. Both names
appear in Settings and in the evidence.

**Startup grace**: the silence part of `bridge.offline`, end-device silence, and
`device.flapping` produce no findings for 15 min after MeshPulse starts or Z2M
restarts. Availability changes during the 15 min after a Z2M restart don't
count towards flapping.

**Flood guard**: while `bridge.offline` or `monitor.mqtt_lost` is open, no new
device-level issues open. Already-open ones keep updating.

## Issue lifecycle

A pure function: `(findings, openIssues, counters, devices, settings, now) →
{ inserts, updates, messages, counters }`. The caller applies the result and
queues the messages in one transaction.

- **Open**: the finding has been present for 2 consecutive runs (configurable
  per rule).
- **Update**: evidence and summary refresh every run. Higher severity is an
  escalation and queues a message, also for acknowledged issues. Lower
  severity updates silently.
- **Resolve**: the finding has been absent for the rule's hold (default 2
  runs; `bridge.offline` 2 min). Queues a resolve message with the duration.
- **Reminder**: Critical every 6 h, Warning every 24 h, Info never. Not for
  acknowledged issues.
- **Muted device**: the issue is stored and shown, no messages are queued.
- **Quiet hours** (default 23:00–07:00 in `TZ`): Warning and Info messages
  (all kinds) are held. At the end of quiet hours, one summary message lists
  what is still open and what opened and resolved overnight. Critical always
  goes through.

## Notifications

```ts
interface Message {
  severity: 'critical' | 'warning' | 'info' | 'resolved';
  title: string; summary: string; action?: string;
  fields: { name: string; value: string }[];
  url?: string;
  kind: 'open' | 'escalate' | 'reminder' | 'resolved' | 'digest';
}
interface Channel { kind: string; send(config: unknown, message: Message): Promise<void> }
```

The registry holds only `discord`. `digest` is used for the quiet-hours summary
and folded bursts.

**Outbox**

- Rows are created in the same transaction as the issue change, one per enabled
  channel whose `min_severity` allows it. `dedupe_key` = `issueId:kind:severity:channelId`
  (reminders add the reminder time) blocks duplicates.
- The worker sends at most 1 message per 2 s per channel. When more than 3 are
  due for a channel, they're folded into one "N new issues" message.
- On failure, retry after 1, 5 and 30 min, then mark failed. HTTP 429 uses
  Discord's `retry_after`.
- A row is marked sent right after a 2xx. A crash in between can resend once.
  This is accepted over losing alerts.

**Discord**: one embed per message. Colours: Critical red, Warning amber, Info
blue, resolved green. Optional `@here` on Critical (channel setting). Fields:
device, LQI, battery, last seen. The link is `PUBLIC_URL/issues/<id>` when
`PUBLIC_URL` is set.

**Secrets**: the webhook URL is encrypted with AES-256-GCM, using a key derived
from `SECRET_KEY` (scrypt).

**Send test**: posts directly, skips the outbox, and returns the result to the UI.

## UI

SvelteKit pages, no component library, minimal CSS. Pages reload their data
every 15 s with `invalidateAll`. All routes except `/login` and `/api/health`
need a session.

- **Overview**: a status banner (green: no open issues or only Info; amber: any
  Warning; red: any Critical), prerequisite warnings, open issues by severity,
  counters (devices online/total, routers online/total, batteries < 25%), and a
  bridge line (Z2M version, uptime, channel, coordinator). A healthy network
  shows a green "All good", the counters and the bridge line.
- **Devices**: a sortable table with name, type, availability, last seen, LQI,
  battery % and V, and open issues. Filters: routers, battery, offline, has
  issues.
- **Issues**: open, acknowledged and resolved tabs. The detail page shows the
  summary, suggested action, evidence, the device's last 50 events, an
  acknowledge button and a device mute button (1 h, 24 h, 7 d, forever,
  unmute).
- **Settings**: thresholds, quiet hours, the Discord channel (webhook URL,
  `@here` on/off, min severity, enabled, Send test), heartbeat URL,
  prerequisites status, failed outbox messages.

## Heartbeat and health

- **Heartbeat**: GET to the heartbeat URL every 60 s, only when MQTT is
  connected and the rules ran in the last 2 min. The URL from Settings wins
  over `HEARTBEAT_URL`. Failures are logged, not retried.
- **`/api/health`**: returns `{ mqtt, lastMessageAt, lastRulesRunAt }`, with 200
  when healthy (connected and rules ran in the last 2 min) and 503 otherwise.
  The Docker healthcheck uses it.

## Configuration

Environment variables: `MQTT_URL`, `MQTT_USERNAME`, `MQTT_PASSWORD`,
`Z2M_BASE_TOPIC`, `DATABASE_PATH` (default `/data/meshpulse.db`), `PUBLIC_URL`,
`TZ`, `SECRET_KEY` (required), `HEARTBEAT_URL`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`.
Behind a reverse proxy: `PROTOCOL_HEADER` and `HOST_HEADER` (SvelteKit 3's
adapter-node no longer reads `ORIGIN`).

## Deployment

Multi-stage Dockerfile (Node LTS), `docker-compose.yml` with a `./data`
volume and a healthcheck, `.env.example`, and a README covering setup, the Z2M
config changes, the broker user's permissions, and Dokploy notes.

## Testing

Vitest. JSONL fixtures in the capture format: `{ "ts", "topic", "payload", "retain" }`.

- **Router**: every topic type, both availability formats, `/set` and `/get`
  ignored, names with `/`, retained device state not counted as live.
- **Rules**: for each rule, it fires, holds and stops, plus the startup grace.
- **Lifecycle**: open after 2 runs, escalate, ack then escalate, reminders,
  mute, quiet hours with a summary, resolve hold.
- **Scenarios** (fixtures through router → rules → lifecycle on a fake clock):
  Z2M restart, mass reconnect after restart, battery swap, renamed device,
  MQTT lost, flood guard.
- **Outbox**: retry with backoff, 429 handling, rate limit, folding, no
  duplicates.
- `scripts/capture.ts` records `zigbee2mqtt/#` to JSONL for later replay tests.

## Risks

- **`bridge.offline` on a quiet network**: 5 min without live traffic can
  happen on a very small mesh. The threshold is a setting, and the real-mesh
  week will show if it needs raising.
- **Payload differences between Z2M 1.x and 2.x**: handled by accepting both
  formats, covered by fixtures. Real captures will be added as they come.
- **Typical-gap learning**: devices that only report on change (contact
  sensors) can have very long gaps. The 25 h cap keeps this from going past
  Z2M's own battery timeout.
